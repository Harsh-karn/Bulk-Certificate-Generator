# RULES — Bulk Certificate Generator

Rules for the author and for any AI assistant used on this project.

## 1. Accuracy rules (documentation and answers)
1. Do not guess or fabricate. If the brief does not specify something, label it as a **proposal** or **open question**.
2. Clearly separate **given requirements** (from the brief) from **author decisions**.
3. Never claim a feature, test, or command works unless it was actually run.
4. Do not invent library behaviour. Check official docs when unsure.
5. Do not state performance numbers that were not measured.

## 2. Scope rules
1. Required functionality is finished before any optional feature.
2. One predefined template only. No template editor, no multiple designs.
3. No features beyond the brief unless listed as optional in TASKS.md.
4. Keep it simple enough that the author can explain every line in an interview.

## 3. Code rules
- Python with type hints on function signatures.
- Keep layers separate: routers (HTTP) → services (logic) → models (data). No business logic in routers.
- One responsibility per module; functions short and named for what they do.
- Configuration (DB URL, storage dir, max recipients) lives in `config.py`, not hard-coded.
- No secrets committed. Use environment variables with safe defaults for local dev.
- Never build file paths from user-supplied strings. Use IDs generated by the server.
- Background tasks open their own DB session.
- Per-certificate work is wrapped so one exception cannot abort the job.
- Use explicit HTTP status codes and a consistent error response shape.
- Comments explain *why*, not *what*.

## 4. API rules
- Bulk by design: one request carries the whole recipient list.
- Responses must expose enough information to tell successes from failures (counts + per-certificate status + error message).
- Do not return file system paths to the client.
- Job creation returns immediately; it does not wait for generation.

## 5. Testing rules
- Every minimum area in the brief has at least one test:
  create job · input validation · certificate generation · job status/progress · individual failure · retrieval.
- Tests use an isolated database and temporary storage directory; they never touch real data.
- Simulate an individual certificate failure deliberately (e.g. patch the renderer to raise for one recipient) and assert the others still succeed.
- Tests must pass from a clean checkout using the documented commands.

## 6. Documentation rules
- README covers all items the brief lists: setup, run, test, submit a request, retrieve certificates, design decisions.
- Every command and example request in the README is copied from something that was actually run.
- Document the processing-model choice with reasoning and limitations.

## 7. Git rules
- Small commits with meaningful messages.
- Generated PDFs, `.env`, virtualenv, and the local DB file are git-ignored.

## 8. AI-usage rules
- AI tools are allowed by the brief, but all code must be understood by the author.
- Before committing AI-generated code, read it and be able to explain it.
- Record non-obvious decisions in MEMORY.md so they can be justified during the interview.
